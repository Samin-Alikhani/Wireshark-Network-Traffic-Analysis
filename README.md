# Wireshark Network Traffic Analysis

## Overview

In this lab, I used Wireshark to look at the packets generated by a DNS lookup,
a ping, and an HTTPS connection on my Mac. I practiced filtering out background
traffic and following each exchange to understand what was happening.

I focused on:

- Choosing the network interface to capture from
- Using display filters to find the packets I wanted to examine
- Matching requests with their responses
- Following one TCP connection
- Reading the TCP handshake and TLS Client Hello and Server Hello messages

## Lab Environment

- **Operating system:** macOS
- **Tool:** Wireshark 4.6.2
- **Capture interface:** Wi-Fi (`en0`)
- **Commands:** `dig`, `ping`, and `curl`
- **Targets:** `example.com` and `1.1.1.1`

## Generating the Traffic

I captured traffic on my Mac while running these commands:

```bash
dig example.com
ping -c 4 1.1.1.1
curl -I https://example.com
```

I left out the original capture because it includes unrelated background
traffic and details about my local network. The screenshots below have local
IP addresses, MAC addresses, and device identifiers covered.

## What I Observed

### DNS Lookup

I filtered for DNS traffic involving `example.com` and found the query and
response. Both had transaction ID `0x9226`, which helped me match them. The
query asked for an A record, used to look up an IPv4 address, and showed the
Internet class (`IN`).

![Sanitized DNS query and response](evidence/dns-query-response-sanitized.png)

### Ping Requests and Replies

The ping produced four ICMP Echo requests and four replies from `1.1.1.1`.
I used their identifiers and sequence numbers to match each reply to its
request. This showed that the target responded to ping during the capture,
though it did not tell me whether other services were working.

![Sanitized ICMP Echo analysis](evidence/icmp-echo-sanitized.png)

### TCP Handshake

I found the HTTPS connection in TCP stream 6. The first three packets showed
the SYN, SYN-ACK, and ACK handshake between client port `64625` and server
port `443`.

Reading the sequence and acknowledgment numbers helped me follow the
handshake. Each side tracks its own sequence numbers, and each SYN counts as
one when the other side acknowledges it.

![Sanitized TCP handshake](evidence/tcp-handshake-sanitized.png)

### TLS Client Hello

In the Client Hello, I found `example.com` in the Server Name Indication (SNI)
field. This helped me confirm that I was looking at the intended connection.

I also saw the TLS versions the client offered, an X25519 key share, and
HTTP/2 (`h2`) and HTTP/1.1 listed through ALPN, the extension used to agree on
an application protocol. These were the client's proposed options; I needed
to look at the server's response to see which TLS settings were selected.

![Sanitized TLS Client Hello](evidence/tls-client-hello-sanitized.png)

### TLS Server Hello

The Server Hello showed TLS 1.3 in the `supported_versions` extension. It also
selected `TLS_CHACHA20_POLY1305_SHA256` and included an X25519 key share.

I learned to check the `supported_versions` extension when reading a TLS 1.3
handshake. Other version fields still showed TLS 1.2 for compatibility, even
though the connection was using TLS 1.3.

![Sanitized TLS Server Hello](evidence/tls-server-hello-sanitized.png)

After the handshake, I saw TLS Application Data in both directions. The TCP
connection later closed with a four-packet FIN/ACK exchange.

## What I Took Away from the Lab

- I initially followed a background connection. Checking the SNI helped me
  find the `example.com` connection I meant to study.
- A successful ping tells me that a host replied at that moment. Checking an
  application takes more than that.
- The Client Hello lists the client's options. The Server Hello shows which
  TLS version and cipher suite the server selected.
- Captures can include unrelated traffic, so I need to check what is visible
  before sharing screenshots.

This lab helped me connect the commands I ran with the packets they produced.
Following the requests, replies, and handshake messages made it easier to
understand how the protocols work together.
